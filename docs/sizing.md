# サイズの規則づくり（M4）の準備：できていること・残り

設計書 12 章の準備部分。実際の比較の計算は、M3（決めた設定）と速さの目処が立ってから行う。

## できていること（crates/sizing）

- `features`：スートに依存しないボードの特徴。
  フロップ：一番高いカードの高さ（A / K / Q・J / T〜8 / 7 以下）、ペア（なし / あり / トリップス）、スート（レインボー / ツートーン / モノトーン）、
  つながり（同じストレートの範囲に入るランクの数：0〜1 / 2 / 3 以上。A は 5 ハイのストレートでも数える）。
  ターン・リバー：新しいカードの種類（ボードがペアになる、フラッシュ完成、ストレート完成、オーバーカード、フラッシュドローの出現（ターンのみ）、ブランク。この順で優先）。
- `flops`：1,755 のフロップ（22,100 通りを同型でまとめたもの。重み付き）と、代表 200・確認用 80 の選び方。
  特徴の組み合わせ（61 種類）ごとに最低 1 つ、残りは実際に配られる頻度に比例して選ぶ。シードで再現できる。確認用は代表と重ならない。
- `rules`：規則の表（JSON）。空欄は「何でもよい」で、一致する項目が一番多い行が勝つ。プレイヤー（IP / OOP）、チェックのあとのベットかどうか、ストリート、特徴で分けられる。`into_size_rule()` でゲーム木のサイズの規則になる。
- `compare`：方法 1。候補のサイズごとに 1 サイズの木を解き、ベットする側の均衡の EV が一番高いものを選ぶ。勝ち残り方式（全候補を 4% で解き、上位 2 つを 1.5% で比べる、が標準）。
- `sizing` コマンド：`sizing select`（代表と確認用のフロップ）、`sizing flops`（1,755 の一覧と特徴）、
  `sizing compare-flops`（M4 の逐次比較 runner）。
- テスト：特徴の例、スートの付け替えで特徴が変わらないこと、1,755 と 22,100 の検算、選び方の再現性と重なりのなさ、規則の優先順位、JSON の往復、
  二極化レンジのリバーで一番大きいサイズが選ばれること。

## 残り

1. **スートの同型との両立は実装済み**：規則の表と street 上書きは M3 の `SizeRule::SuitInvariant` を返す。
   上書き元もスートに依存しない規則を使う。M3 のサンプル検査と実木検査に失敗した場合は、規則を維持したまま同型削減を無効にする。
   EV の BB 換算は `GameSpec.units_per_bb` に従う。
2. **ターン・リバーの比較**：フロップの均衡から、ターン（リバー）開始時の両者の到達レンジを取り出す API を solver に足し、
   そのレンジからターン（リバー）だけを解いて比べる。
3. **規則の作成**：代表の状況での比較結果から、表の行を作る（同じ特徴の組み合わせで多数決、EV の差が小さいものはまとめる）。
4. **確認**：確認用の状況で、規則のサイズと最適なサイズの EV の差（損失）を測る。目標は平均でポットの 0.1% 未満、最大 0.5% 未満。


## M4 試行 runner

`cargo build --release` 後、例えば次を実行する（長時間の実レンジ計測）。

```sh
target/release/sizing compare-flops --out data/m4 --report docs/benchmarks/m4-trial.md
```

入口はリポジトリ内の `tools/m4_trial.py` を Python 3 で起動し、以後の引数をそのまま渡す。
既定の `--binary` は sizing 実行ファイルと同じディレクトリの `cli`、
`--sizing-binary` は実行中の sizing。後続の同名引数で明示的に上書きできる。
`sizing compare-flops --help` は runner のオプションを表示する。
フロップ選択は既存の `select_flops(20, 0, 20261015)` のままで、
20 枚では全 61 特徴 bucket の網羅はできない。選択アルゴリズムや製品レンジは変更しない。

## ターン・リバーのサイズの比べ方（M4 の後半、計画）

フロップの規則が決まったあとに行う。M3 の「途中から解く」機能（ストリート開始時の到達レンジの取り出し、`solve-subgame`）を使う。

1. **出発点**：代表のフロップごとに、規則のフロップのサイズ（ターン・リバーは仮の 66%）で、フロップから解く（精度 1% 程度）。
2. **ターンの状況**：フロップの流れ（チェック・チェック、ベット・コール。レイズ・コールは頻度が低いので後回し）×
   ターンのカードの種類（ボードがペア、フラッシュ完成、ストレート完成、オーバーカード、フラッシュドローの出現、ブランク）ごとに、
   そのフロップで種類に当てはまるカードを 1〜2 枚選ぶ。
3. **比べ方**：ターンの開始時点の両者のレンジから、ターン以降だけを解く。ベットする側ごとに別々に比べる：
   - OOP が先に打つベットのサイズ（IP 側のサイズは 66% のまま）
   - OOP がチェックしたあとの IP のベットのサイズ（OOP 側は 66% のまま）
   候補 4 つを粗く（5%）解き、上位 2 つを細かく（0.5%）解いて、ベットする側の EV で選ぶ（フロップと同じ）。
4. **リバー**：ターンの代表の状況から、同じ考え方でリバーのカードの種類ごとに比べる（リバーだけの木は小さく速い）。
5. **規則**：特徴（フロップの特徴 ＋ カードの種類 ＋ 流れ ＋ ベットする側）ごとに、選ばれたサイズを多数決でまとめ、規則の表の行にする。
6. **量の目安**：代表 200 フロップ × 2 つの流れ × 6 種類 × 2 つのベットする側 ＝ 約 4,800 の状況（ターン）。1 状況あたり候補 4 つの粗い解（数十秒）＋ 上位 2 つの細かい解（数分）。EC2 で並べて回す前提。
