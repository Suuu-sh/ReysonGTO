# ReysonGTO 設計書（ポストフロップ CFR ソルバー）

作成日：2026-10-15
状態：第 2 版（実装前。外部 crate の利用、精度の目標、プリフロップのソルバー、API を反映）

## 1. 目的

ReysonAI のヘッズアップのポストフロップのレンジ表を、**自前の CFR ソルバー**で GTO 近似として作る。
「早く・安く・正確に」を優先し、**木は常に 1 判断 1 ベットサイズ**にする。どのサイズを使うかは、
候補の中で EV が一番高いものを**規則**（ボードの特徴 → サイズ）で選ぶ。

- 作るもの：**ポストフロップのソルバー**と**プリフロップのソルバー**（15 章）。
  ポストフロップは前提となるプリフロップのレンジで答えが変わるので、**全フロップの本番計算は、プリフロップのソルバーでレンジを確定させてから**行う。
- 精度：表示に使う本番の結果は、エクスプロイタビリティを**ポットの 0.3% 以下**（できれば 0.2%）にする。
- 実行環境：まずは開発用の Mac（Apple Silicon、10 コア、約 25GB）。全フロップの本番計算は
  AWS EC2 の大きいコンピュート向けインスタンス 1 台（例：c8g / c7a の 192 vCPU）で、同時に十数ボードを解く想定。

## 2. 守ること（クリーンルーム）

- 既存の OSS ソルバー（postflop-solver、TexasSolver、wasm-postflop など。多くは AGPL）の
  **ソースコードは読まない・写さない・依存しない**。比べてよいのは、それらの**出力**（戦略の CSV、エクスプロイタビリティの数値）だけ。
- アルゴリズムは公開論文と一般知識（CFR、CFR+、Discounted CFR、ベストレスポンス）から自分で実装する。
- 外部の crate は、**MIT、Apache-2.0、BSD などの緩いライセンスのものに限って使ってよい**（例：serde / serde_json、rayon、clap、zstd、anyhow）。
  AGPL、GPL、LGPL のものは使わない。追加するときは `cargo deny`（または同等の確認）でライセンスを検査する。
- ポーカーのソルバーや役の判定の crate は使わない（中身を自前で持つため）。
- このリポジトリは公開されているので、ReysonAI の製品データ（プリフロップのレンジなど）は**コミットしない**。
  レンジは実行時に外部の JSON ファイルから読み込む（9 章）。テスト用には、意味のない合成レンジだけを入れる。

## 3. 前提となるゲームの設定（2026-10-15 合意）

| 項目 | 設定 |
|---|---|
| ゲーム | 6 人のキャッシュゲーム、100BB、アンティなし、オープン 2.5BB |
| ポストフロップ | HU のみ（SRP と 3BET ポット。4BET ポット以降は対象外） |
| レーキ | ポットの 5%、上限 3BB。勝った側の受け取りから差し引く（ショーダウン、相手のフォールドのどちらも）。ポストフロップは必ずフロップを見ているので常にかかる |
| ドンク | なし。プリフロップのコール側が OOP のとき、フロップの最初の判断はチェック固定。OOP がプリフロップの最後のレイザーなら、OOP が先にチェックかベットを選べる。ターンとリバーは、どちらも先にベットできる（通常のアクション） |
| ベットサイズ | 1 判断につき 1 サイズ。サイズは規則で決める（12 章）。候補：SRP は 33 / 66 / 100 / 125%、3BET ポットは 25 / 33 / 66 / 100 / 125% |
| レイズ | 直前のベットの 3 倍（「3 倍」は相手のベット額の 3 倍の額までレイズする、という意味）。回数は無制限（スタックの上限まで） |
| オールインへのまとめ | ベットやレイズの額が、そのプレイヤーの残りスタックの 67% 以上になるときは、オールインにまとめる |
| フォールド | ベットやレイズに直面したときだけ選べる（チェックで済むときにフォールドはない） |

## 4. 全体の構成

Cargo のワークスペースで、役割ごとに crate を分ける。

```
ReysonGTO/
  Cargo.toml                 ワークスペース
  crates/
    cards/      カード、コンボ、役の判定、スートの同型
    ranges/     レンジの読み込み、ボードとの重なりの除外、コンボの番号づけ
    tree/       ゲーム木の設定と構築（サイズ、レイズ、オールイン、レーキ）
    cfr/        CFR の本体（反復、後悔値の更新、平均戦略、ベストレスポンス）
    solver/     上をまとめた API（フロップから解く、ターンから解く、リバーから解く）
    sizing/     サイズの規則づくり（候補の比較、特徴量、規則、損失の確認）
    preflop/    プリフロップのソルバー（15 章）
    cli/        コマンド（solve, batch, sizing, bench, compare）
  tests/        結合テスト（トイゲーム、比較）
  docs/         設計書、計測の記録
```

## 5. カードと役の判定（crates/cards）

- カードは 0〜51 の整数（`rank * 4 + suit`）。コンボは 1,326 通りで、`(c1, c2)` を 0〜1325 の番号にする。
- 7 枚の役の強さは、**ボードが 5 枚決まった時点で、全コンボの強さの順位を一度だけ計算**して使う。
  役の判定は自前で実装する（ビットマスクでフラッシュとストレートを判定し、ランクの数え上げでペア系を判定する方式）。
  全 7 枚の組み合わせ（1.3 億通り）を素朴な判定と突き合わせるテストを置く。
- **スートの同型**：フロップのスートの構成に対して、同じ形になるスートの入れ替えを求める。
  ターンとリバーのカードのうち、入れ替えで同じになるものはまとめて、重み（何枚分か）を付けて計算する。
  例：レインボーのフロップでは、ターンのカード 49 枚が、ずっと少ない種類にまとまる。

## 6. ゲーム木（crates/tree）

### 6.1 設定

```
TreeConfig {
  starting_pot, effective_stack,          // チップの単位（下記）
  oop_can_lead_flop: bool,                // OOP が最後のレイザーなら true
  bet_size: SizeRule,                     // (ストリート, ボード, そこまでの流れ) -> ベットの割合
  raise_multiplier: 3.0,
  allin_merge_ratio: 0.67,
  rake_rate: 0.05, rake_cap: 3BB,
}
```

- チップは整数で扱う。**1BB = 1,000 単位**。ベット額は四捨五入して単位に揃える。
- `SizeRule` は、ストリートとボード（とそのストリートでの最初のベットかどうか）からサイズを返す関数。
  フロップのサイズはフロップのカードだけで決まり、ターンとリバーはカードごとに変えてよい（12 章の規則で決める）。
  **1 判断にサイズは 1 つ**なので、木の形は 1 サイズの木と同じになる。

### 6.2 構造

- 各ストリートの行動の木を作り、ストリートの区切りに**チャンスノード**（ターン、リバーのカード）を置く。
- ノードは配列（アリーナ）に詰める。行動ノード、チャンスノード、終端（フォールド、ショーダウン、オールインの決着）の 3 種類。
- 各行動ノードが持つもの：行動するプレイヤー、選択肢の数、子の位置、そのノードのポットとスタック、
  後悔値と戦略の保存場所（13 章の配置）の先頭位置。
- オールインのあとは、残りのカードを配ってショーダウンするだけ（行動ノードなし）。
- レイズの連鎖は「3 倍、ただしスタックの上限まで。残りの 67% 以上ならオールイン」で、自然に止まる。
  100BB で 33% のベットから始めると、数回でオールインに届く。

## 7. CFR の本体（crates/cfr）

### 7.1 アルゴリズム

- **Discounted CFR**（α = 1.5、β = 0、γ = 2）を標準にする。CFR+ も切り替えで使えるようにして、収束を比べる。
- **両プレイヤーを交互に更新**する。1 反復 = OOP の更新と IP の更新を 1 回ずつ。
- **ベクトル形式**：木を 1 回たどるたびに、各プレイヤーの全コンボの到達確率をベクトルで持ち、まとめて計算する
  （ボードと重なるコンボを除いた、そのプレイヤーのコンボだけの密なベクトル）。
- 戦略は**後悔値の正の部分に比例**させる（後悔値がすべて 0 以下なら一様）。
- 平均戦略は、DCFR の重み（γ）を付けて累積する。

### 7.2 終端の計算

- **フォールド**：相手のレンジの到達確率の合計から、自分のコンボと重なる相手のコンボを除く。
  カードごとの合計（52 個）を使って、「全体 − 自分の 1 枚目を含む − 2 枚目を含む ＋ 同じコンボ」で O(n) にする。
- **ショーダウン**：両者のコンボを役の強さの順位で並べておき（5 章で計算済み）、
  弱いほうから相手の到達確率を累積して「自分より弱い相手の合計」と「強い相手の合計」を求める。
  重なるカードの除外は、フォールドと同じくカードごとの累積で行う。同じ強さはまとめて引き分けとして扱う。O(n)。
- **レーキ**：勝った側の受け取りを「ポット − min(ポット × 5%, 3BB)」にする。引き分けはレーキを引いた残りを半分ずつ。
  レーキがあるとゼロサムではなくなるので、エクスプロイタビリティの定義は 7.3 のとおりにする。

### 7.3 ベストレスポンスとエクスプロイタビリティ

- 平均戦略に対する各プレイヤーのベストレスポンスの価値を、木を 1 回たどって正確に計算する。
- エクスプロイタビリティ = { (BR_OOP − 平均戦略での OOP の価値) + (BR_IP − 平均戦略での IP の価値) } / 2、
  を**フロップ開始時のポットに対する %** で表す。レーキありでも意味のある定義にする。
- 停止条件：エクスプロイタビリティが目標以下（本番は 0.3% 以下、できれば 0.2%。サイズの規則づくりの比較は 1〜2%）、
  または反復の上限、または時間の上限。エクスプロイタビリティは数反復ごとに計算する。

## 8. 並列化（rayon）

- 一番重いのはターンとリバーの部分なので、**ターンのカード（同型でまとめた後）ごとに仕事を分けて**、スレッドで並列に計算する。
  チャンスノードの下の子をスレッドに配り、結果（そのプレイヤーの各コンボの価値のベクトル）を足し合わせる。
- 並列化は rayon を使う。各スレッドは作業用のバッファを使い回す（スレッドごとの領域）。
- 結果の足し合わせは、毎回同じ順番で行い、**同じ入力なら同じ結果になる**（決定的）ようにする。
- 1 ボードの中のスレッド数は 8〜16 程度で頭打ちになる想定。大きいインスタンスでは、**複数のボードを同時に**解いて CPU を使い切る（14 章）。

## 9. レンジの入力（crates/ranges）

- レンジは外部の JSON から読む（リポジトリにはコミットしない）。形式：
  `{ "player": "BTN", "combos": { "AhKd": 0.85, ... } }` または ハンドクラス単位 `{ "AKs": 0.5, ... }`（コンボに均等に配る）。
- ReysonAI 側で、各局面（例：BTN オープン → BB コール）のレンジをこの形式に書き出すスクリプトを用意する（ReysonAI リポジトリ側の作業）。
- ボードと重なるコンボは除き、残ったコンボに番号を振る。プレイヤーごとにベクトルの長さが違ってよい。

## 10. 保存の形式とメモリ

### 10.1 計算中のメモリ

- 行動ノードごとに「選択肢の数 × 行動するプレイヤーのコンボ数」の後悔値と平均戦略を持つ。
- 精度とメモリの切り替え：
  - **f32**（標準、正確）
  - **i16 の量子化**（ノードごとに倍率を持つ）。メモリが約半分になる。大きい木のときに使う。
- 解く前に、木の大きさから必要なメモリを見積もり、上限を超えるならエラーにする（途中で落ちないように）。
- 目安：1 サイズの木、100BB の SRP で、1 ボード 数 GB〜10GB 程度（実測で確定させる）。

### 10.2 結果の保存

- 本番で保存するのは**フロップの戦略だけ**（OOP と IP のフロップのすべての判断、コンボ単位とハンドクラス単位）。
- 1 ボード 1 ファイル（JSON を zstd で圧縮）。置き場所は Cloudflare R2（ReysonGTO 側）で、16 章の API から返す。書き込みは一時ファイルに書いてから名前を変えて置き換え、途中で止まっても壊れないようにする。
- メタデータ：設定一式、使ったサイズ、反復の数、時間、エクスプロイタビリティ、ソルバーの版、入力レンジのハッシュ。
- ターンとリバーは保存せず、必要になったらその場で解く（11 章）。

## 11. 途中から解く（サブゲーム）

- **ターンから解く・リバーから解く**機能を作る。入力は「ボード、ポット、スタック、両者のその時点のレンジ（コンボごとの重み）」。
- 用途：
  1. 12 章のサイズの規則づくり（ターン、リバーのサイズを比べる）
  2. 将来、ユーザーがターンやリバーを選んだときに、その場で解く
- ターンからの木はフロップからの木よりずっと小さいので、数秒〜数十秒を目標にする。リバーは 1 秒前後。

## 12. サイズの規則づくり（crates/sizing）

### 12.1 比べ方（方法 1）

ある状況で、候補のサイズごとに **1 サイズの木を別々に解き**、ベットする側の**ゲーム全体の EV**
（その判断の時点での均衡の価値。チェックを含む戦略全体の価値）が一番高いサイズを選ぶ。
選ぶための計算は粗くてよい（エクスプロイタビリティ 1〜2%）。

- **勝ち残り方式**：まず全候補をとても粗く解き（3〜5%）、明らかに低いサイズを外してから、残りを少し精度を上げて比べる。

### 12.2 特徴量

| ストリート | 特徴の例 |
|---|---|
| フロップ | 一番高いカード、2 番目と 3 番目のカード、ペアの有無、スートの数（レインボー、ツートーン、モノトーン）、つながり具合（ストレートの可能性） |
| ターン | フロップの特徴 ＋ ターンのカードの種類（ブランク、オーバーカード、ボードがペアになる、フラッシュの完成・フラッシュドローの出現、ストレートの完成）、そこまでの流れ（フロップでベットされてコール、チェックで回った） |
| リバー | ターンと同様 ＋ ドローが外れたかどうか |

### 12.3 手順

1. **代表の状況を選ぶ**：フロップは 1,755 種類から特徴が偏らないように約 200 を選ぶ。ターンとリバーは、代表のフロップから、カードの種類ごとに数枚ずつ選ぶ。
2. **候補のサイズを比べる**：12.1 の方法で、各状況の最適なサイズと、サイズごとの EV を記録する。
   ターンとリバーは、フロップの（粗い）均衡の到達レンジを入力にして、11 章のサブゲームで比べる。
3. **規則にまとめる**：特徴からサイズを決める**決定表**（人が読める表）にする。
   どの規則がどの状況から作られたかを記録しておく。
4. **確認**：規則づくりに使っていない確認用の状況（フロップ 50〜100 など）で、規則が選んだサイズと最適なサイズの **EV の差（損失）** を測る。
   目標は、平均でポットの 0.1% 未満、最大で 0.5% 未満。超える種類があれば規則を細かくする。

### 12.4 規則の分け方

規則は「ベットする側（IP か OOP か）」「そのストリートの最初のベットか（チェックのあとのベットか、先に打つベットか）」で分けて作る。
たとえば、OOP がチェックしたあとの IP のベットと、OOP が先に打つベットは、別の規則にする。

## 13. メモリの配置と高速化の工夫

- 後悔値と戦略は「ノード × 選択肢 × コンボ」の順に連続した配列に置き、内側のループがコンボの方向に連続して読むようにする（自動ベクトル化が効く形）。
- 作業用のバッファはスレッドごとに使い回し、反復中にメモリを確保しない。
- リバーの終端の計算（ショーダウン）が一番多いので、強さの順に並べた配列とカードごとの累積を事前に作っておく。
- スートの同型でターンとリバーの計算量を減らす（5 章）。
- 計測を先にして、遅い場所を確かめてから最適化する（`cli bench` で反復あたりの時間と、部分ごとの時間を出す）。

## 14. まとめて解く（cli batch）

- `batch --spot BTN_open_BB_call --flops all --concurrency N --threads-per-board M`
- 1,755 フロップ（スートの同型の代表）を順に解き、1 ボード 1 ファイルで保存する。保存済みで検証が通るボードは飛ばす（**再開できる**）。
- 進み具合を 1 行 1 ボードの記録（JSONL）に書く：ボード、サイズ、反復、時間、エクスプロイタビリティ、メモリの最大値。
- 結果は R2 に書き出す（S3 互換の API。アップロードは CLI のオプションで行う）。
- スポットインスタンスで止められても、計算中のボードだけをやり直せばよい。

## 15. プリフロップのソルバー

ポストフロップの答えは、前提となるプリフロップのレンジで変わる。今の ReysonAI のプリフロップのレンジは AI が作ったもので GTO ではないので、
**プリフロップもソルバーで解き、そのレンジを入力にしてポストフロップの本番計算を行う**。

### 15.1 ゲーム

- 6 人、100BB、アンティなし、レーキはプリフロップで決着したときはかからない（フロップを見ていないため）。
- 行動のメニューは ReysonAI の今の設定に揃える：オープン 2.5BB（SB のオープンは別に決める）、3bet は IP で 3 倍・OOP で 4 倍程度、
  4bet は 2.2〜2.5 倍、5bet はオールイン。コール、フォールドあり。SB のリンプ（コンプリート）を入れるかは 19 章。
- 3 人以上がフロップに進む流れ（マルチウェイ）は、まずは扱いを限定する（例：コールドコールを許さない、または許した場合の価値を近似する）。

### 15.2 フロップ以降の価値

プリフロップのソルバーの一番の難所は、「フロップに進んだときに、そのハンドがどれだけの価値を持つか」。段階を分けて精度を上げる。

1. **v1：エクイティ × 実現率**。各ハンドの相手のレンジに対するエクイティを計算し、ポジション、ポットの種類、ハンドの種類ごとの**実現率**を掛ける。
   実現率の初期値は一般的な目安で置く。
2. **v2：ポストフロップのソルバーから実現率を学ぶ**。代表の局面とボードをポストフロップのソルバーで解き、
   ハンドクラスごとの実現率（均衡の価値 ÷ エクイティ × ポット）を集計して v1 の値を置き換える。
3. **反復**：v2 のプリフロップのレンジでポストフロップを解き直し、実現率を更新する、を数回繰り返して落ち着かせる。

### 15.3 解き方

- プリフロップの木は小さいので、CFR（DCFR）でハンドクラス単位またはコンボ単位で解く。1 回の計算は数分〜数十分の見込み。
- 出力：各局面のハンドクラスごとの頻度（ReysonAI のプリフロップのレンジの形式に変換できる形）。

## 16. API（結果の受け渡し）

結果は ReysonAI の D1 に入れず、**ReysonGTO 側の API で返す**。ReysonAI は API を呼んで表示するだけにする。
（ReysonAI の D1 にテーブルを足すと、MW3 の審査記録と保全用の目印の検査に波及するため。）

```
ソルバー（Rust） ──結果──> R2 ──> Cloudflare Worker（API） <── ReysonAI
                                         （将来）その場で解くサーバー
```

| API | 内容 |
|---|---|
| `GET /v1/spots` | 解き終わった局面と、結果のバージョンの一覧 |
| `GET /v1/spots/{局面}/flops/{フロップ}` | フロップの戦略（ハンドクラス単位とコンボ単位、使ったサイズ、精度、ソルバーの版） |
| `GET /v1/preflop/{局面}` | プリフロップのソルバーの結果 |
| `POST /v1/solve`（将来） | ターン・リバーから解く。結果は R2 に保存して、同じ問い合わせは再計算しない |

- **バージョン**：解き直すたびに結果のバージョンを上げ、API は「今の版」を指す。ReysonAI はデプロイなしで新しい版に切り替わる。
- **キャッシュ**：同じ版の結果は変わらないので、エッジで長くキャッシュする。
- **アクセスの制限**：ReysonAI からの呼び出しだけを許す（API キー、または ReysonAI の Worker を経由する）。
- **その場で解く処理**は Worker では CPU の制限で無理なので、小さい EC2 に Rust のプログラムを置くか、WebAssembly にしてブラウザで解く（19 章）。

## 17. 正しさの確認（テスト）

| テスト | 内容 |
|---|---|
| 役の判定 | 7 枚の全組み合わせを素朴な判定と突き合わせる |
| 終端の計算 | O(n) のショーダウンとフォールドを、素朴な O(n²) の計算と突き合わせる（ランダムなレンジ、重なりあり） |
| 同型 | スートの同型をまとめた場合とまとめない場合で、戦略とベストレスポンスが一致する |
| トイゲーム | 答えが分かっている小さいゲーム（リバーだけの、二極化したレンジ対ブラフキャッチャー）で、ブラフの比率と防御の頻度が理論値に一致する |
| ベストレスポンス | 純粋戦略に対するベストレスポンスの価値が、全探索の結果と一致する |
| 決定性 | 同じ入力とスレッド数で、結果がビット単位で同じ |
| レーキ | 上限 3BB が効く場合と効かない場合で、払い出しが正しい |
| 外部との比較 | 同じ設定（ボード、サイズ、レイズ、レンジ）で解き、OSS ソルバーの**出力**（戦略の CSV）とハンドクラスごとに比べる。差の平均と最大を記録する |

## 18. 性能の目標と段階

| 段階 | 内容 | 目標 |
|---|---|---|
| M1 | cards、tree、cfr の最小版。リバーだけ・ターンからのサブゲーム。トイゲームのテスト | テストがすべて通る |
| M2 | フロップから解く。外部の出力との比較（ベンチマークと同じ設定：ベット 50%、レイズ 2.5 倍・無制限、ドンクあり、レーキなし） | 戦略の差が小さい。時間はベンチマーク（Mac で 0.27% まで約 12.6 分、メモリ約 9GB）と同等以上 |
| M3 | 3 章の設定（レーキ、ドンクなし、3 倍レイズ、オールインへのまとめ、サイズの規則の差し込み） | 1 ボードを 0.3% まで 15 分以内（Mac） |
| M4 | サイズの規則づくり（12 章）。まずフロップ 20 ボードで試してユーザーに見せる | 損失の目標を満たす規則 |
| M5 | プリフロップのソルバー v1（15 章、エクイティ × 実現率） | レンジが ReysonAI の形式で出せる |
| M6 | 実現率をポストフロップのソルバーから学ぶ（v2）、反復してレンジを確定 | — |
| M7 | まとめて解く（14 章）。確定したレンジで BTN vs BB SRP の全 1,755 フロップ（0.3% 以下） | 再開できる。EC2 でも動く |
| M8 | API（16 章）と ReysonAI での表示 | — |
| M9 | ほかの HU SRP 局面、3BET ポット | — |

### 18.1 見積もりについて

本書の時間とメモリの数字は、別に動かした既存ソルバー（ベット 50%、レイズ 2.5 倍、1 ボード約 13 分、約 9GB、0.27%）の実測からの**概算**で、
自作のコードではまだ測っていない。木が小さいこと（1 サイズ、3 倍レイズ、オールインへのまとめ、ドンクなし）、スートの同型、収束の工夫、
SIMD とメモリの配置で、これより速くできる可能性がある。逆に、0.3% までの収束やレーキの影響で遅くなる可能性もある。
**M2（ベンチマークと同じ設定）と M3（3 章の設定）の実測で、時間・メモリ・費用の見積もりを更新する。**

## 19. 決まっていないこと

- 本番の精度を 0.3% にするか 0.2% にするか（表を見比べて決める）。
- ReysonAI からの API の呼び方（ブラウザから直接か、ReysonAI の Worker を経由するか）。
- プリフロップの木の細部（SB のリンプ、SB のオープンのサイズ、コールドコールとマルチウェイの扱い）。
- サイズの規則は、ベットする側（IP か OOP か）と、そのストリートの最初のベットかどうかで分けて作る（12 章の詳細化）。
- ターンとリバーをその場で解く場所（ブラウザで WebAssembly にするか、サーバーか）。
- 量子化（i16）を標準にするかどうか（精度への影響を測って決める）。
