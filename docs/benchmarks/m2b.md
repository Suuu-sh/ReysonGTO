# M2b: 固定入力の収束・計測改善

実行日: 2026-10-15。M2 の未達結果は `docs/benchmarks/m2.md` に保全します。
作業ブランチは `feat/m2b_speed`。commit / push / reset / checkout / rebase / stash は実施していません。外部依存の追加と `Cargo.lock` の変更はありません。
最終のフルフロップ実行は完了しました。**0.3% 以下・15 分以内は未達**です。40 分枠と最大 RSS 10 GB 以下は満たしましたが、M2b を性能目標の達成とは扱いません。

## 境界と固定条件

- `docs/design.md` と M2 の比較境界を維持。既存 OSS ポーカーソルバーのソースや禁止ディレクトリは参照しません。比較に使うのはコピー済み出力だけです。
- 固定ボードはターン `QsJh2h3c`、フロップ `QsJh2h`。レンジは既存の `data/ranges/{bb_call,btn_open}.json` を読み取り専用で使用し、頻度の変更・対称化はしません。
- ポット 5.5 BB、スタック 97.5 BB、50% bet、2.5x raise、OOP lead あり、レーキなし、all-in merge なし、1 BB = 65536 単位。
- exploitability は初期ポットに対する %。停止目標は常に **0.3% 以下**。終了コード 0 と目標到達を区別します。
- ターンで選んだ設定がフルフロップでも速いとは限りません。反復数だけ、または未収束の処理時間だけで速度勝利とはしません。

## 再現・資源計測

`tools/m2b_bench.py` は JSON matrix の各ケースを逐次実行します。ビルドや入力変換は行いません。
各 solve ごとに別の `measure_command.py` プロセスを起動するため、最大 RSS は前の solve やテレメトリ subprocess の累積ではありません。
`resource.json` の wall / CPU / 最大 RSS と、solver の setup / training / metrics / solve 秒を区別します。
profile の worker 秒は並列 worker の総和であり、wall 秒の割合ではありません。

```sh
python3 tools/m2b_bench.py --config data/m2b/step2-config.json --out data/m2b/new-run
```

出力先は新規ディレクトリのみ受け付けます。各ケースに command / stdout / stderr / resource / progress / solution / telemetry を保存し、全体の `summary.json` と `manifest.json` を残します。
manifest のバイナリ SHA256 と入力 SHA256 は実行物・入力の識別用です。
**`source_files_at_launch` は起動時の working tree のスナップショットで、保存済みバイナリがそのソースからビルドされたことを保証しません。** ビルド対応は別のビルド記録で確認します。

### OS テレメトリの限界

約 10 秒間隔と終了後に `vm_stat`、`sysctl vm.swapusage`、`pmset -g therm`、`ps` を取得します。
この環境では `ps` と swap の sysctl が権限不足になる場合があり、その stderr と終了コードも保存します。昇格は行いません。
`pmset` の「警告の記録なし」は温度測定でも、熱スロットリングがなかった証明でもありません。
`vm_stat` はホスト全体の累積値で、他プロセスの影響を含みます。
getrusage の major fault / swap が 0 でも、メモリ圧迫・圧縮・熱・外部負荷の不存在は断定できません。
短いターンでは開始・終了の 2 点だけになることがあります。既存の step2 実行開始後に追加した終了時テレメトリは、その実行へ遡って適用されません。

## Step 6: compact metadata

`StateWork` を 176 → 144 bytes、付随 metadata 配列を 32 → 12 bytes/node に圧縮しました。合計 **52 bytes/node**、フル木 2,450,180 nodes では **127,409,360 bytes の構造上の差**です。加えて children / orbits / scratch / member の Vec capacity を必要数に合わせ、最小 capacity 4 由来の余剰を除きます。後悔値・平均戦略の i16 payload と頻度は変更しません。

| ターン条件 | 反復 | exploitability % | solve 秒 | 最大 RSS bytes |
| --- | ---: | ---: | ---: | ---: |
| before | 105 | 0.289457515 | 7.046052 | 376,946,688 |
| compact | 105 | 0.289457515 | 7.207596 | 375,144,448 |

最終 exploitability は **0.28945751488794175% が bit 一致**。ターンでは solve は約 2.3% 遅く、RSS は 1,802,240 bytes（約 0.48%）減でした。速度改善とは扱いません。
生データ: `data/m2b/step6/{manifest,summary}.json`。

**構造サイズの理論差・Vec の割当容量・保守的 memory estimate・実測最大 RSS・OS 圧縮量は別の指標**です。52 bytes/node の削減が、そのまま同量の RSS 削減になるとは限りません。OS 圧縮・ページの residency・余剰 capacity の影響もあるため、フル木の実測を別に残します。

## 最終フルフロップ・戦略差・判定

### 最終結果: 目標未達

### 採否と未解決

- **維持・採用:** 非対称頻度、正確な BR、i16、DCFR α=1.5 / β=0 / γ=4、10 threads / grain 1 / profiling on。adaptive metrics、fused policy/update、grouped showdown、compact metadata を最終実行に含めました。個別の単一ターン改善率は合算しません。

- **未達:** 0.3% 以下、15 分以内、参照と同精度での時間・RSS 比較。40 分枠と 10 GB RSS は満たしましたが、それだけで完了目標達成とはしません。
- **次の候補（未実装・未検証）:** ボードでブロックされたコンボをより密に詰める、slab / scratch の帯域削減、near metrics を 10 にする比較（現状 5、停止検出が遅れる可能性あり）、ホストメモリ状態を制御した逐次再測定。速度・精度の改善は保証しません。
