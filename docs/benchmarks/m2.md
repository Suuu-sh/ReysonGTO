## 入力・木・同型の確認

`tools/export_benchmark_ranges.py` は指定ノードの BB call 頻度をコンボごとに取得します。
BTN は `BTN_open` の `open / 100` を、そのクラスの各コンボに同じ頻度として設定します。
ここではクラス頻度を 4 / 6 / 12 で割りません（loader の「クラス総重量」形式とは異なるため、
exporter が明示コンボ形式へ展開します）。

- 元 JSON の SHA256 は両方とも preflight の `file_sha256` と完全一致。
- ボード除去後 BB 1176 / BTN 690。BB の各コンボについて
  `自身の頻度 × 重ならない BTN 頻度の総和` を参照 CSV の root reach と比較し、
  最大絶対差 `2.8927229266e-5`、相対許容誤差 `1e-6` 内。
  upstream の `range_sha256` シリアライズ方式は再実装していません。
- `allin_merge_enabled=false` を CLI `--no-allin-merge` で選択。
  `--units-per-bb 65536` で参照のチップ精度を合わせます。
  デフォルトの設計値 1000 のままだと、レイズ総額 17.1875 BB が 17.188 BB に丸められます。
  これは比較専用の明示的な設計差で、通常利用のデフォルトは変更しません。
- `Raise(x)` の `x` はその判断で追加投入する額です。
  street-total のレイズ列は 2.75 → 6.875 → 17.1875 BB となります。
- `cargo run --release -p tree --example m2_tree_audit` の物理木:
  2,450,180 ノード、935,520 判断、2,268,536 アクション枠、3,784 チャンス、1,510,876 終端。
- BB の c↔d 置換による頻度差は最大 `0.9038676965`。
  **この実レンジでは非自明な同型を使用できず、削減枝数は 0**。
  性能のために非対称レンジを対称化していません。

## 計測してからの最適化

M1 の各ノードが持っていた reach / value / current-strategy 配列を、深さ別の再利用 scratch と
最初の並列 chance 分岐ごとの scratch に変更しました。永続状態は後悔値と平均戦略の 2 本です。
実際の配列確保前に mode 別にメモリを見積もり、f32 / i16 を選択します。

### f32 / i16 の制御比較 (修正前のターンサブゲーム)

フル入力・`QsJh2h3c`・同じポット/スタック/サイズ/精度・merge 無効・100 反復・10 threads。

| モード | solve 秒 | 訓練 秒 | 最大 RSS bytes | exploitability |
| --- | ---: | ---: | ---: | ---: |
| f32 | 3.4373 | 2.8809 | 382,189,568 | 0.36916969% |
| i16 | 3.5736 | 2.9995 | 344,637,440 | 0.38641839% |

この小さい木では量子化はメモリを削減しますが、速度・精度を改善しませんでした。
フルフロップ f32 は見積もり 23,511,280,218 bytes が設定上限 18,874,368,000 bytes を超え、
安全に事前拒否しました。24 GB のマシンを圧迫する実行は行わず、フル比較は i16 を採用します。
生データ: `data/m2/turn-{f32,i16}{,-time}.json`、`data/m2/preflight-f32{.log,-time.json}`。

macOS sandbox では `/usr/bin/time -l` が `kern.clockrate` を取得できないため、
`tools/measure_command.py` の単一子プロセスに対する `getrusage(RUSAGE_CHILDREN)` で
最大 RSS / CPU / wall time を取得します。RSS は推定 payload や OS の memory footprint とは異なります。

### 計測後に採用した変更

- 各判断で行っていた DCFR の `powf` を走査開始時に計算。
- 量子化はノードごと、戦略正規化はコンボごとに逆数を計算し、内側の除算を削減。
- ボードと重なるコンボの正規化をスキップ。
- 平均戦略の累積から初期の自分のコンボ頻度を相殺。
  同じコンボの全アクションに掛かる定数なので正確な算術では戦略を変えません。
  i16 では初期頻度 `1e-8` のコンボが丸めで消え、一様戦略に戻る不具合を回帰テストで確認して修正。
  subnormal の量子化倍率の underflow / reciprocal overflow も保護します。

| 同じフル入力・10 反復・γ=2 | 訓練 秒 | solve 秒 | exploitability | 最大 RSS bytes |
| --- | ---: | ---: | ---: | ---: |
| コンパクト化直後 | 94.2659 | 119.7076 | 65.35981270% | 7,051,870,208 |
| 上記変更後 | 87.5083 | 111.5854 | 65.35941275% | 9,747,054,592 |

後者の永続 regret + average は `8,466,176,352 bytes`。
同じ反復数で訓練時間は約 7.2% 短縮しましたが、どちらも未収束であり、
**目標精度までの高速化を示す結果ではありません**。各 1 回の実行で、RSS の差にも OS の状態が影響します。
後者の部分別 worker seconds: 判断 455.423、showdown 316.073、fold 105.101、chance 16.798。
生データ: `data/m2/optimized-i16{,-time}.json`。

### 初回の計測後に追加した改善

- ショーダウンでは同順位の前後の prefix を使い、順位ごとの 52 カード配列初期化と
  相手コンボの二重加算を除去。既存 value scratch を使い、新規確保はしません。
- 自分の BR 判断では、自分の平均戦略の decode / 正規化と reach の戦略乗算を省略。
  BR の値は相手の reach だけに依存し、自分の戦略は最大化するためです。
- i16 の policy は共通 node scale を相殺して整数配列から直接正規化。
  f32 も policy 取得時のコピーを除去し、更新時は in-place とします。
  `Engine::strategy()` と走査は同じ正規化を使います。
- 2 / 3 アクションの正規化ループを展開。一般のアクション数も維持します。

同じターン入力・100 反復・γ=3 を旧バイナリと新バイナリで順番に実行しました。

### 戦略差: コンボとクラス、アクション別

比較対象はルート OOP BB（1176 コンボ / 169 クラス）と、OOP チェック後 IP BTN（690 / 119）。
参照 CSV の **compatible-joint `reach_weight` を両戦略に共通の重み**として使用します。
クラスの最終戦略も同じコンボ重みで再集計し、クラスの重みはその合計です。
これにより、到達分布の差を戦略の確率差に混ぜません。最大差は各行に対する最大絶対差です。
比較 CLI は設定・チップ精度・アクション・コンボ／クラス集合・参照クラス集計の整合性、
ルートの正規化 compatible-joint 到達重み（L1 許容値 1e-4）を確認して成功しました。

平均・最大・全体頻度差は **pp**、参照／最終の全体頻度は **%** です。
