# プリフロップ・ソルバー設計書（M5〜M6）

作成日：2026-10-15
状態：初版（実装前）。全体の設計書 docs/design.md の 15 章を詳しくしたもの。

## 1. 目的

6 人・100BB のプリフロップを CFR で解き、各局面のハンドクラスごとの頻度を出す。
このレンジを入力にしてポストフロップの本番計算（M7）を行うので、**ポストフロップより先にレンジを確定させる**。

## 2. ゲームの設定（ReysonAI の `configs/cash-6max-100bb.json` に揃える）

| 項目 | 値 |
|---|---|
| 人数・スタック | 6 人（UTG, HJ, CO, BTN, SB, BB）、100BB、アンティなし、ブラインド 0.5 / 1 |
| レーキ | 5%・上限 3BB。**フロップを見ないで終わったときはかからない**（no flop no drop） |
| オープン | 2.5BB。SB は 3.5BB |
| SB のリンプ | SB はコンプリート（1BB）できる。BB はリンプにアイソ（3.5BB）かチェック、リンプ後のリレイズは 10.5BB |
| 3bet | IP 8BB、OOP 12BB、SB オープンに対しては 10.5BB |
| スクイーズ | IP 12BB、OOP 13BB、コーラーが 1 人増えるごとに +2.5BB |
| 4bet | IP 26BB、OOP 20BB、SB の BB の 3bet に対しては 24BB。4bet の代わりにオールインも選べる |
| 5bet | 4bet の 2.2 倍のレイズ、またはオールイン。レイズの額が残りスタックの 67% 以上ならオールインにまとめる。その次（6bet）はオールインのみ |
| コール | 各段階でコール（コールドコールを含む）できる |

ReysonAI 側の設定ファイルは読むだけで、ReysonGTO には「設定の JSON を読み込む」機能だけを入れる（製品データはコミットしない）。

## 3. 木

- 先に行動するプレイヤーから順に、選べる行動（フォールド / コール / 決まったサイズのレイズ / オールイン）で木を作る。
- サイズは上の表の「何 BB まで」で決まる。スタックを超えるときはオールイン。
- 行動が閉じたとき（全員がコールかフォールド）にフロップへ進む終端、1 人を残して全員フォールドした終端、オールインの決着の終端の 3 種類。
- **未実装（P4 の前に実装する）**：4bet でのオールインの選択肢、5bet の 2.2 倍レイズ、6bet のオールインのみ。
  今の `crates/preflop/src/tree.rs` は 4bet を決まった額だけで作り、オールインは 5bet から出す（docs/benchmarks/m5.md に記載）。
- 最初のオープンへのコールドコールはあり（スクイーズの局面ができる）。4bet 以降に新しくコールドコールで入る行動は入れない（2026-10-17 決定）。

## 4. 解き方

- **コンボ単位（1,326）のベクトル形式の CFR**（DCFR）。6 人それぞれの到達確率のベクトルを持つ。
- 6 人のゲームはゼロサムの 2 人ゲームではないので、CFR の収束先はナッシュ均衡とは限らない（粗い相関均衡）。
  実務のプリフロップ・ソルバーと同じく、各プレイヤーの**ベストレスポンスで得をする量の合計**（BB）で収束を測り、十分小さくなったら止める。
- プレイヤーの間のカードの重なり（ブロッカー）は、終端の計算で扱う（途中の到達確率は独立に持つ）。

## 5. 終端の価値

### 5.1 フォールドで終わった場合

残った 1 人がポットを得る。レーキなし。

### 5.2 オールインで決着した場合

エクイティは正確に計算する（5.4 の表）。フロップを見るので、レーキがかかる。

### 5.3 フロップに進んだ場合（ポストフロップの価値の近似）

ここが一番難しい。段階を分ける。

- **v1：エクイティ × 実現率**
  ハンドの価値 = （ポット − レーキの見込み）× エクイティ × 実現率 −（そのハンドがすでに入れた額）。
  実現率は「ポットの種類（SRP / 3BET / 4BET / リンプ）× ポジション（IP / OOP）× ハンドの種類（ペア、スーテッド、オフスーツ、高さ）」の表で持つ。
  初期値は一般的な目安（IP は 1 前後、OOP は 0.85 前後、スーテッドやつながったハンドは高め、弱いオフスーツは低め）で置き、表を設定ファイルにする。
- **v2（M6）：ポストフロップのソルバーから実現率を学ぶ**
  代表の局面とフロップ（例：各局面 30〜50 フロップ）を ReysonGTO のポストフロップ・ソルバーで解き、
  ハンドクラスごとの「均衡での価値 ÷（エクイティ × ポット）」を集めて表を置き換える。
- **反復**：v2 の表でプリフロップを解き直し、そのレンジでポストフロップを解き直して実現率を更新する、を数回くり返して落ち着かせる。
- **3 人以上でフロップに進む場合**：エクイティは 3 人以上の勝率（5.4 の表）を使い、実現率はマルチウェイ用の表（v1 は控えめな値）で近似する。
  ReysonAI のマルチウェイのポストフロップは AI 方式なので、ここは近似のままでよい。

### 5.4 エクイティの表

- 2 人：169 × 169 のハンドクラスどうしの勝率（引き分けは半分）。カードの重なりを考えた正確な計算、
  または十分なサンプル数のモンテカルロで事前に作り、ファイルに保存する（M1 の自前の役判定を使う）。
- 終端では「自分のコンボ × 相手の到達レンジ」の積で計算する。ハンドクラスの表を使い、コンボの重なりは補正する。
- 3 人以上：よく出る組み合わせだけ、サンプルで近似する（v1）。

## 6. 出力

- 各局面（例：UTG のオープン、BTN の UTG オープンへの対応）のハンドクラスごとの各行動の頻度（JSON）。
- ReysonAI のプリフロップのレンジの形式（`opening-ranges.json` など）へ変換するのは ReysonAI 側の作業にする。
- 結果は API（docs/design.md 16 章の `GET /v1/preflop/{局面}`）で返す。

## 7. 確認

| 確認 | 内容 |
|---|---|
| 小さいゲーム | 2 人・1 回のレイズだけのプッシュ／フォールドのゲームで、既知の答え（ナッシュのプッシュ・コールの範囲）に一致する |
| エクイティ | よく知られた対戦（AA 対 KK、AKs 対 22 など）の勝率が正しい |
| レーキ | フロップを見ないときにかからない、上限 3BB |
| 外部の目安 | オープンの合計頻度（UTG, HJ, CO, BTN, SB の 5 つ）だけを外部の参考値と比べる（±3pt 程度）。ほかの局面は自前の確認で判断する。参考値は表の下に記す |
| 収束 | ベストレスポンスで得をする量の合計が、反復とともに小さくなる |

### 7.1 オープン頻度の参考値

| 項目 | 内容 |
|---|---|
| 出どころ | GTO Wizard の「Cash 100bb」（6 人）の事前計算の解。2026-10-17 にユーザーが画面で確認した値 |
| 分かっている設定 | 100BB、ブラインド 0.5 / 1、オープン 2.5BB、SB のオープン 3.5BB と SB のコンプリートあり、各局面でオールインの選択肢あり |
| 分からない設定 | ソルバーとそのバージョン、レーキ、3bet 以降のサイズ、コールドコールの扱い。画面に出ていないため記録できない |
| 値（合計頻度のみ） | UTG 17.5%、HJ 21.7%、CO 27.9%、BTN 40.6%、SB レイズ 34.4% ＋ コンプリート 13.7% |

設定が一部しか分からないので、この値は**ゲームの定義の違いを含む目安**であり、回帰テストの基準には使わない。
±3pt を外れたときは、まず設定の違い（とくにレーキと 3bet 以降のサイズ）で説明できるかを確かめる。

## 8. 段階

| 段階 | 内容 |
|---|---|
| P1 | 設定の読み込みと木の作成。木の大きさ（ノード数）の確認 |
| P2 | エクイティの表（2 人の 169×169、3 人の近似） |
| P3 | 2 人だけの小さい木（例：BTN 対 BB のオープン・3bet・4bet）で CFR を動かし、形を確認する |
| P4 | 6 人の木全体を v1（エクイティ × 実現率）で解く。オープンの合計頻度を外部の目安と比べる |
| P5（M6） | ポストフロップのソルバーから実現率を学び（v2）、反復してレンジを確定する |

## 9. 決まっていないこと

- 実現率の初期値の表（P4 の前に決める）。
- 2 人の 169×169 の表を、正確な計算にするかサンプルにするか（時間で決める）。
